# generated-default

A **Dual-Plane Agent Stack (DPAS)** application: a device operations dashboard
whose assistant operates the app through *governed capabilities*, never the
DOM. Generated by [`create-dpas-app`](https://www.npmjs.com/package/create-dpas-app).

```bash
pnpm install   # or npm / yarn / bun
pnpm dev       # open http://localhost:3000
```

**No API key, no database, no configuration.** Press **Run guided demo** in the
assistant panel: a deterministic scenario runner executes the golden flow —
filter to offline devices in Milan, select them, disable them behind a real
confirmation — through the exact same pipeline a live model uses.

## The one idea worth stealing

The app exposes two planes of capabilities and never blurs them:

| | `view:*` — presentation plane | `domain:*` — authoritative plane |
|---|---|---|
| Meaning | what the currently open page can do | operations valid with no UI at all |
| Examples | `view:devices.filters.set`, `view:devices.table.selectRows` | `domain:devices.list`, `domain:devices.disable` |
| Owner | [Agent Surface](https://www.npmjs.com/package/@agent-surface/core), registered by components | [oRPC Agent](https://www.npmjs.com/package/@orpc-agent/core) over real oRPC procedures |
| Executes | in this browser tab | on the server, re-authorized every call |

`domain:devices.disable` is the interesting one: it is **not** a direct model
tool. It reaches the model only as a *contextual reference* — hidden without
permission, unavailable until rows are selected, its `deviceIds` bound to the
live selection and locked, and gated by a single-use, input-bound
confirmation. One operation, one canonical identity, one execution path.

## Configure a live model (optional)

**From the UI** — click the settings icon in the assistant panel (or
“Connect”), paste an [OpenRouter](https://openrouter.ai/keys) key, pick a
model. No restart. The key is held in the server process's memory: it is
never written to disk, never returned to the browser (you only ever see
`••••1234`), and never enters a client bundle — the agent loop runs
server-side, so the browser never needs it. Restarting clears it.

Because that key is shared by everyone hitting the same process, runtime
entry is enabled in development and disabled in production builds unless you
set `ALLOW_RUNTIME_MODEL_KEY=true`.

**From `.env`** — the durable option for a deployment:

```bash
MODEL_PROVIDER=openrouter    # or: anthropic · openai
OPENROUTER_API_KEY=sk-or-... # or: ANTHROPIC_API_KEY / OPENAI_API_KEY
```

Restart, then ask the assistant:

> Show me the offline devices in Milan, select the visible devices, and disable them.

Mastra plans over the composed catalog; view tools stream back to your
browser; the destructive call still ends in the same confirmation card. The
guided demo keeps working regardless.

## Where everything lives

```
src/
  features/devices/        the feature: components register their own view
    components/            capabilities next to the state they describe;
    capabilities/          devices-table.tsx also binds the contextual
    domain/manifest.ts     domain reference (the frontend exposure ceiling)
  server/
    orpc/procedures.ts     THE domain operations (UI, agent, tests — one code path)
    agent/runtime.ts       oRPC Agent governance: registry, policies, audit
    auth/session.ts        demo identity (viewer/operator), server-signed
    db/                    zero-config embedded JSON store
  agent/
    surface/               Agent Surface registry + oRPC bridge (browser half)
    host/                  the Agent Host: protocol.ts, catalog.ts, wire-names.ts,
                           client-dispatch.ts, transport-client.ts, server-compose.ts,
                           correlation (identity.ts), errors.ts
    runtime/               Mastra agent, instructions, run limits, scripted model
    experience/            assistant-ui adapter, tool renderers, confirmation card
    demo/scenario.ts       the deterministic guided demo
    inspector/             trace store for the Agent Inspector
  components/              app shell, UI primitives, assistant panel, inspector UI
  app/                     Next.js routes: /dashboard, /architecture, /api/*
```

## Identity demo

The header switcher swaps between two server-signed demo identities:

- **Olivia — operator** may disable devices (after confirmation);
- **Vik — viewer** may only look. For Vik, `domain:devices.disable` is not
  "disabled" — it is *absent*, indistinguishable from never existing.
  **Authority hides; state discloses.** Watch the Inspector's catalog tab
  while switching.

The switcher re-signs a cookie server-side (`src/server/auth/session.ts`);
role claims in request bodies are never read. Replace that one file to plug in
real auth.

## The Agent Inspector

The assistant panel's **Inspector** tab shows, live:

- **Catalog** — every capability the model can currently see, its
  availability (with reasons), confirmation requirements, and locked bindings;
  plus what is hidden from the current identity and why.
- **Timeline** — correlated events from every layer (surface, host, runtime,
  domain), with invocation and confirmation ids.
- **Map** — the topology, and the rule it encodes: one model-facing catalog
  never implies one execution authority.

## Commands

```bash
pnpm dev          # run the app
pnpm test         # capability contract tests, host tests, governance tests — no LLM
pnpm test:e2e     # Playwright: guided demo, live scripted-model mode, a11y, mobile
pnpm lint         # eslint
pnpm typecheck    # strict TypeScript
pnpm build        # production build
```

Everything in `pnpm test` and `pnpm test:e2e` runs without any model
provider: e2e uses a scripted `LanguageModelV2` (`MODEL_PROVIDER=mock`)
through the full live pipeline, so CI never needs credentials.
